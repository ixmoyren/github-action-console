# Release Console — Phase 1 (Skeleton)

Status: ready-for-agent
Type: spec
Feature: release-console

## Problem Statement

发布桌面软件的人必须同时应付 GitHub 的三个互不相连的界面：Actions 里翻 workflow run 和 job 日志、Releases 里核对产物与下载链接、以及自己心里（或一张表格里）记着 stable / beta 通道现在到底指向哪个 tag。仓库一多、分发目标一多（GitHub Releases、Mac App Store、直接下载），"这个版本在各个发布目标上走到哪一步了"就没人能一眼答上来。浏览器里没有一个桌面入口能把"登录 → 选仓库 → 看构建 → 看日志与产物"连成一条路。

用户现在缺的是 **骨架**：一个能安全登录 GitHub、列出自己名下仓库、进入指定仓库并查看其 Actions 运行与日志的桌面应用——后续所有的发布能力都长在这个骨架上。

## Solution

一个跨平台桌面控制台（macOS / Windows / Linux），用 GPUI Kit 构建界面，用 octocrab 访问 GitHub。

用户通过 **GitHub Device Flow** 登录（PAT 作为兜底），应用把 token 存进操作系统钥匙串，并在下次启动时恢复登录态。登录后应用列出用户名下的全部仓库，支持按更新时间或推送时间排序、按名称过滤；选中一个仓库后进入仓库工作区，左侧导航在「工作流 / 运行」之间切换。用户可以看到该仓库的 workflow 列表与 workflow run 列表（状态、分支、事件、触发者、时间），打开某次运行的详情查看各 job 与 step 的状态，直接读取 job 级原始日志，按需下载整次运行的日志包，并列出与下载该次运行产出的构建产物。

界面上始终可见应用自身的版本号、构建目标（target triple）与打包配置标识，让"我在用哪个构建"一目了然；状态栏同时显示当前登录用户与 GitHub API 限流余量。

按 ADR-0001，本应用 **不构建、不上传任何二进制**；它只观察。构建与签名/公证/上传由 CI runner 承担。

## User Stories

1. 作为发布者，我想要用 GitHub Device Flow 登录，这样我不用手工创建和粘贴 token 就能授权应用。
2. 作为发布者，我想要在登录时看到 GitHub 给出的一次性 user code 和验证地址，这样我能知道下一步在浏览器里做什么。
3. 作为发布者，我想要一键复制 user code 并直接打开验证地址，这样登录流程不用来回切换窗口。
4. 作为发布者，我想要在等待授权时看到"等待中"状态与剩余有效期，这样我知道应用没卡死。
5. 作为发布者，我想要在授权成功后立刻进入应用，这样登录不打断我的心流。
6. 作为发布者，我想要在 device code 过期时看到明确提示并能重新发起，这样我能从失败中恢复。
7. 作为发布者，我想要在 Device Flow 不可用（例如未配置 client_id）时改用粘贴 PAT 登录，这样我仍然能用这个应用。
8. 作为发布者，我想要在 PAT 权限不足时看到"缺少哪些 scope"的明确提示，这样我能自己修正 token 而不是对着 403 猜。
9. 作为发布者，我想要登录状态被持久化，这样重启应用后不必重新授权。
10. 作为发布者，我想要 token 只存在操作系统钥匙串里（macOS Keychain / Windows Credential Manager / Linux Secret Service），这样我的凭据不会以明文落盘。
11. 作为发布者，我想要在持久化的 token 失效（被撤销或过期）时被带回登录页并看到原因，这样我不会对着一堆加载失败发呆。
12. 作为发布者，我想要登出时把钥匙串里的 token 一并清除，这样共享机器上不留凭据。
13. 作为发布者，我想要在 macOS、Windows、Linux 上得到一致的操作体验，这样换机器不用重新学。
14. 作为发布者，我想要看到我名下全部仓库（含私有仓库）的分页列表，这样我不必一次把它们全加载进内存。
15. 作为发布者，我想要按名称搜索我的仓库，这样仓库多了以后我能快速定位。
16. 作为发布者，我想要按最近更新时间或最近推送时间排序仓库，这样我能先看到正在动的项目。
17. 作为发布者，我想要在仓库列表里区分私有与公开仓库，这样我不会选错可见性。
18. 作为发布者，我想要在仓库为空或加载失败时看到空状态与错误态，这样我能判断是自己没有仓库还是请求出了问题。
19. 作为发布者，我想要选中一个仓库后进入它的工作区，这样我可以专注于这一个仓库的操作。
20. 作为发布者，我想要在左侧导航里在「工作流」和「运行」之间切换，这样我不会在仓库内有多个入口时迷路。
21. 作为发布者，我想要看到该仓库全部 workflow 的列表，这样我知道有哪些自动化流程存在。
22. 作为发布者，我想要看到某仓库的 workflow run 列表及其状态、分支、事件、触发者与时间，这样我能判断最近一次跑的是什么、成没成。
23. 作为发布者，我想要按状态、分支或 workflow 过滤 run 列表，这样我能只关注失败或只关注某个流程。
24. 作为发布者，我想要正在运行的 run 被自动刷新，这样我不用手动点刷新就能看到它什么时候结束。
25. 作为发布者，我想要打开一次 run 的详情看到各 job 与 step 的状态，这样我能定位是哪个阶段出的问题。
26. 作为发布者，我想要直接读取某个 job 的原始日志文本，这样我能看到出错的那几行，而不必先下载再解压。
27. 作为发布者，我想要在日志视图里滚动、搜索并复制文本，这样我能把报错片段贴给别人。
28. 作为发布者，我想要按需下载整次运行的日志包，这样我能在本地留档或做更深的分析。
29. 作为发布者，我想要看到一次运行产出的构建产物列表，这样我知道它到底产出了什么。
30. 作为发布者，我想要下载单个构建产物，这样我能拿到中间产物做验证。
31. 作为发布者，我想要一键在浏览器里打开这次运行对应的 GitHub 页面，这样我能跳回 GitHub 处理应用没覆盖的事。
32. 作为发布者，我想要状态栏始终显示当前登录用户，这样我确认自己是以哪个身份在操作。
33. 作为发布者，我想要状态栏显示 GitHub API 的限流余量与重置时间，这样我知道何时该等一等。
34. 作为发布者，我想要应用始终显示自己的版本号、构建目标（target triple）与打包配置标识，这样我能确认在用哪个构建、判断是否需要更新。
35. 作为发布者，我想要网络请求失败时看到可见的错误提示而不是白屏或崩溃，这样我能知道发生了什么并重试。
36. 作为发布者，我想要在触发 GitHub 二级限流时看到退避提示，这样我不会以为应用坏了。
37. 作为发布者，我想要应用记住我上次选中的仓库，这样重启后我能直接回到工作现场。
38. 作为发布者，我想要界面跟随系统的明暗主题，这样长时间使用不刺眼。
39. 作为发布者，我想要界面文案是中文，这样我不用在专业术语和英文之间切换。
40. 作为发布者，我想要应用在下载大日志或大产物时界面保持可交互，这样我能同时做别的事。

## Implementation Decisions

### 模块与分层

- 单一 Cargo 包，同时产出 **library** 与一个 **极薄的 binary**。binary 只做组合根（初始化 tokio runtime、打开数据库、构造真实 gateway、启动 GPUI 窗口），不含业务逻辑。
- library 内部分为四个模块边界：
    - **domain**：纯域类型与纯函数，不含 IO。包括发布的术语（发布版本、通道、通道指针、分发目标、发布目标、打包配置、发布清单、构建、构建产物、发布资产、发布状态）、发布状态推导、通道指针解析、发布清单解析与校验、发布目标 × 版本到产物的匹配。这些全部是可直测的纯函数。
    - **github**：`GitHubGateway` port trait，以及它的 octocrab 适配器实现。
    - **store**：SQLite 持久化（SQLx）。
    - **app**：用例层，依赖 `GitHubGateway` 与 store，独立于 GPUI。
    - **ui**：GPUI Kit 视图，只调用 app 层的用例，不直接接触 octocrab 或 SQLx。

### 唯一的注入缝：`GitHubGateway`

- app 层只依赖 `GitHubGateway` trait，生产环境注入 octocrab 适配器，测试注入脚本化 fake。
- trait 的操作用域语言命名、返回域类型（不是 octocrab 的 model 类型），错误统一为应用自己的错误类型，至少能区分：认证失效、权限不足、限流、未找到、网络/传输失败。
- Phase 1 需要的操作：发起 device flow 授权、轮询 device flow、列出当前用户仓库（分页 + 排序）、按名称过滤仓库、列出仓库 workflow、列出 workflow run（支持状态/分支/workflow 过滤）、读取单次 run、列出 run 的 jobs 与 steps、读取 job 原始日志、下载 run 日志包、列出 run 的构建产物、下载单个构建产物、读取 API 限流状态。
- 适配器保持 **薄**：只做 octocrab 调用与域类型映射，不承载业务规则、不做重试之上的策略。
- 后续阶段的 manifest 读写、workflow_dispatch 触发、release 与资产读取都作为 **新增 trait 方法**加入，不改变这个缝的位置。

### 认证与凭据

- Device Flow 主路径：需要一个 GitHub OAuth App 的 `client_id`（callback 可留空、勾选 Device Flow、授权 `repo` 与 `workflow`）。`client_id` 在构建期注入，不硬编码进源码，也不随版本库提交真实值；缺失时自动降级为 PAT 路径并提示原因。
- PAT 兜底：粗粒度需要 `repo` + `workflow`；细粒度需要 `Contents: RW`、`Actions: RW`、`Workflows: RW`。权限不足时明确列出缺哪个 scope。
- token 只进 OS 钥匙串；SQLite 只存账号元数据（登录名、主机）与非敏感偏好。
- 主机默认 `github.com`，但认证与 API 基址作为可注入配置预留，为将来支持 GitHub Enterprise Server 留口子；Phase 1 不实现企业版。

### 运行时与并发

- 进程级唯一 `tokio::runtime::Runtime`，全部 octocrab 调用在其上执行；结果通过 GPUI 的 `Task` / channel 回到 UI，UI 状态只在 GPUI 侧被修改（ADR-0002）。
- 重活（日志/产物下载、分页拉取）走 GPUI 的 background executor 或 tokio，不阻塞渲染。
- 正在运行的 run 由一个轮询任务驱动刷新，任务可取消、在切换到别的仓库或视图时停止。

### 下载与内存

- octocrab 的日志与产物下载是 **一次性读进内存**的，没有流式接口。因此下载必须：先取元数据（大小/类型），超过阈值要先让用户确认，并在后台任务里写盘，避免大 payload 卡住 UI。
- 不实现任何二进制上传；本应用在 Phase 1 完全不产生大文件上行（ADR-0001）。

### 持久化

- SQLx（async，配 tokio）+ SQLite。
- Phase 1 的表：账号元数据、偏好（如上次选中的仓库）、以及可选的短期缓存。
- `通道指针`、`发布目标` / `打包配置` 的定义表属于后续阶段；Schema 演进需保持向后兼容。
- 发布清单（`.github/release-console.yml`）是发布目标与打包配置定义的真相源，但读写与 PR 流程属于后续阶段（ADR-0003、ADR-0004）。

### 应用信息展示

- 版本号来自构建期包版本；构建目标来自编译期 target triple；打包配置标识来自构建期注入的环境变量（缺失时显示为未指定）。
- 三者渲染在标题栏或状态栏的固定位置，任何页面都可见。

### 界面

- 中文单语。文案集中在一个字符串模块，不引入 i18n 框架。
- 主题跟随系统明暗。
- 应用外壳：仓库选择（列表 + 搜索 + 排序）→ 仓库工作区（侧边栏：工作流 / 运行）→ run 详情（jobs/steps 树 + 日志面板 + 产物列表）。
- 所有列表视图具备：加载态、空态、错误态。
- 错误与限流以非阻塞通知呈现，不弹阻塞对话框打断操作。

### 错误处理

- 统一错误类型在 app 边界归一化，UI 只消费归一化后的分类与用户可读文案。
- 认证失效（401）→ 清理凭据并回到登录页；权限不足（403 且非限流）→ 提示缺失 scope；限流（403/429 且有 rate-limit 信号）→ 退避并提示重置时间；未找到（404）→ 视图级空态。

## Testing Decisions

- **什么是好测试**：只验证外部行为——给定 `GitHubGateway` 的输入与它返回的数据，app 层用例应当产生什么结果、发出什么状态迁移、落什么库。不断言 octocrab 的调用细节，不测私有函数，不测 GPUI 渲染。测试应当能在无网络、无 GitHub 凭据的环境下全量运行。
- **被测试的模块**：
    - app 用例层：登录状态机（含 device flow 轮询、过期、降级、失效恢复）、仓库列表的分页/搜索/排序、run 列表的过滤与轮询启停、日志与产物的取用路径（含大 payload 阈值行为）、错误分类到 UI 提示的映射。
    - domain 纯函数：发布状态推导、通道指针解析、发布清单解析与校验、发布目标 × 版本到产物的匹配。这些直接测，无需任何替身。
    - store：对 **真实的内存 SQLite** 做读写往返（账号元数据、偏好、缓存），验证迁移可重复执行。
- **缝的使用**：`GitHubGateway` 是唯一注入缝，测试用脚本化 fake 覆盖成功、空、分页、限流、权限不足、认证失效、网络失败等响应序列。
- **先例**：本仓库目前没有测试先例（代码是空壳），因此本 spec 建立第一批测试约定：集成测试放在顶层测试目录，驱动 library 的公开用例 API；纯域逻辑用模块内单元测试；不引入任何依赖网络的测试。后续所有阶段沿用同一批缝与约定。

## Out of Scope

- **阶段 2（触发与构建）**：展示版本号/发布目标/打包配置的完整管理界面、用 `workflow_dispatch` 触发构建、取消与重跑、围绕发布的构建状态/日志/产物监控。
- **阶段 3（发布看板与分发）**：发布看板视图与发布状态列、通道管理与通道指针的持久化、发布清单的读取/写入与分支 + PR 提交流程、GitHub Releases 与发布资产（Intel/Arm macOS、Windows 下载链接）、Mac App Store 分发路径、配置的 YAML 导入导出。
- **创建/编辑 workflow 文件**：阶段 3 之后；需要 YAML 编辑器与写权限的复杂度单独处理。
- **GitHub Enterprise Server**：主机可配置的接口预留，但企业版认证与 API 兼容不在本阶段。
- **国际化**：中文单语；i18n 框架推迟到确有双语需求时。
- **本地构建/签名/公证/上传**：永不进入本应用（ADR-0001）。
- **多账号同时登录**：Phase 1 单账号。
- **发布内容的编辑**（release notes、tag 创建）：Phase 1 只读。

## Further Notes

- 关键决策已落在 ADR 中，实现时须遵守：
    - ADR-0001：由 CI runner 构建并上传发布资产；本应用只触发与观察，绝不搬运大二进制。
    - ADR-0002：进程级单一 tokio runtime，与 GPUI 自有执行器桥接，UI 状态只在 GPUI 侧变更。
    - ADR-0003：仓库内的发布清单是发布目标与打包配置定义的真相源；SQLite 只存指针与缓存。
    - ADR-0004：发布清单的变更走分支 + PR，绝不直接写默认分支。
- 术语以 `CONTEXT.md` 为准；写代码、起测试名、写 issue 标题时使用其中的标准词，不要漂移到 `_Avoid_` 列出的同义词。
- 三阶段路线图的共同前提：本应用是通用型多仓库控制台，控制台自身跑 macOS / Windows / Linux，被发布的产物的平台与架构由发布目标描述，与应用自身平台解耦。
- 阶段 1 的完成度判定：登录 → 选仓库 → 打开最近一次 run → 读到其 job 日志这条路径可用；断网与二级限流有可见提示且不崩溃；冷启动后三次点击内到达 run 详情。
- 已知外部约束（来自侦查，非本应用可改）：octocrab 的日志/产物/资产上传均为内存内缓冲、无流式；`workflow_dispatch` 的 inputs 无类型且最多 10 个扁平字符串；GitHub 单资产上限 2 GiB。这些约束在阶段 2/3 设计时会再次出现。
