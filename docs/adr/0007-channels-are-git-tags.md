# Channels are git tags

LTS / latest / dogfood 是 **仓库里的 git tag**，不是控制台自己记的指针。发布一条通道 =
把同名 tag 指到一个提交上（已经存在就移过去）；tag 推上去就触发发布工作流，看板随后显示
这次运行里各个发布目标的 job 走到哪儿了。

考虑过的做法：

- **控制台本地记指针（ADR-0005 那套）**：能表达"某个目标还停在上一个版本"，但那个事实只
  存在于这台机器上——换台机器、换个人、或者直接看 GitHub，都看不出来。发布这件事必须
  落在仓库里，否则"发到 latest 了吗"永远要靠控制台的数据库回答。
- **让 tag 名带版本（`latest-v0.1.0`）**：能一眼看出通道指向哪个版本，但每发一次就多一个
  tag，"latest 现在指哪儿"要遍历所有 tag 才知道；而且它逼着发布流程先有一个版本号。
- **只用版本 tag（`v0.1.0`），通道另记**：等于回到指针那套，只是把指针放在别处。

## 后果

- 通道是 **移动的 tag**：`latest` 昨天指 A、今天指 B，这是它的正常用法。控制台建 tag 时
  已经存在就移动它（`PATCH /git/refs/tags/<tag>`，force）。
- 发布工作流 **对任何 tag 都跑**（`on.push.tags: ['**']`）：通道 tag 和版本 tag 都是 tag，
  谁推上来都该构建一次，不该由工作流去挑名字。挑版本号的规则仍然在 `plan` 里
  （tag 名像版本才当版本，否则取代码里的版本）。
- **通道 tag 不是版本号**。tag 名像版本（`v1.2.3` / `1.2.3`）才当版本用，否则版本取自代码
  （`Cargo.toml`）——于是 `latest` 这次构建的产物叫 `github-action-console-0.1.0-windows.msi`，
  挂到 `latest` 这个 Release 上。Release 挂的是 **触发它的那个 tag**，版本号只用来命名文件。
- 看板的一格 = 一个发布目标在一个通道 tag 上的样子，状态直接取自这次 tag 运行里属于该目标的
  job（模板把 job 命名成 `目标名 · 平台/架构 · 产物`，前缀就是发布目标名）。构建成功就是
  "已发布到这条通道"；带模拟步骤的目标停在"待签名公证"。
- 控制台里那套本地指针（`ChannelPointer`、store 里的表、看板上的"发布"按钮）随之作废：
  "已登记发布"这个事实变成"仓库里有这个 tag，且它的运行里这个目标的 job 过了"。
