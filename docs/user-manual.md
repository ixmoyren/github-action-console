# 用户手册：一次完整的发布旅途

这份手册跟着一个具体的人走一遍： **你**要给自己维护的桌面应用发一个版本——从登录，到把四个平台的
产物拿到手里。每一步都写清楚三件事：你做什么、你看到什么、背后发生了什么；最后是"卡住了先看
哪里"。

> 前提：一个 GitHub 账号；一个有（或愿意有）GitHub Actions 的仓库；仓库里是一个 Cargo 项目。
> 例子里的名字用本仓库自己：`ixmoyren/github-action-console`。
> 术语以 [CONTEXT.md](../CONTEXT.md) 为准。

---

## 0. 装好、跑起来

```bash
cargo run
```

Linux 还要装窗口系统与字体相关的开发库（见 [README](../README.md#快速开始)）。第一次启动会：

- 在系统数据目录建一个 SQLite 文件（`github-action-console/console.sqlite`，Linux 上是
  `~/.local/share/…`，macOS 是 `~/Library/Application Support/…`，Windows 是 `%APPDATA%\…`），
  用来记住上次打开的仓库；
- 在日志里报出这个二进制自己的三件事（版本号、构建目标、打包配置）。不开窗口也可以问它：

```bash
cargo run -- --build-info
```

下载默认落在 **系统的「下载」目录**（macOS `~/Downloads`、Windows 的 Downloads 已知文件夹、
Linux 的 XDG `XDG_DOWNLOAD_DIR`）；系统说不上来时退回
`<数据目录>/github-action-console/downloads`。

要连内网或走代理：登录页右上角的齿轮（设置）开一个子窗口，填代理地址保存即可。这个入口挂在
登录页上——登录之后想改，先登出。

---

## 1. 登录

窗口打开是登录页，两条路：

**A. Device Flow（推荐）**

1. 点「使用 OAuth 登录」。
2. 填你自己 OAuth App 的 **Client ID**（GitHub → Settings → Developer settings → OAuth Apps；
   这个 App 不需要回调地址，Device Flow 用不上）。
3. 应用向 GitHub 要一次性代码，屏幕上出现「一次性代码」和「打开验证地址」：
    - 「复制代码」，再点「打开验证地址」跳到 GitHub；
    - 在浏览器里输入代码、授权。
4. 界面显示「等待授权中…」和「有效期（秒）」。授权完成即进入仓库列表。

**B. PAT 兜底**

点「使用 Personal Access Token 登录」，粘贴 token（粗粒度要 `repo` + `workflow`；细粒度要
Contents、Actions、Workflows 三项读写）。权限不够时状态栏会直接说缺什么。

**背后**：token 只写进操作系统钥匙串（macOS Keychain / Windows Credential Manager / Linux
Secret Service）；Ctrl/⌘-Q 再打开仍是登录态，点右上「登出」会把它从钥匙串里清掉。

---

## 2. 选仓库

登录后是仓库列表：

- 「按名称搜索仓库」过滤；「按最近更新」/「按最近推送」切换排序；
- 每行是仓库名、可见性（私有/公开）、默认分支、最近提交与提交日期；
- 「加载更多」翻页，「刷新」重新拉第一页。

点仓库名进入它的 **工作区**。左上「← 返回仓库列表」随时退出；应用会记住这次选的仓库，下次启动
直接回到这里。

---

## 3. 认识工作流：哪条是发布流

工作区左边是仓库的 workflow 列表，右边是选中那条的内容。你会看到两种东西：

- **已有的 workflow**（比如 `.github/workflows/ci.yml`）：点一下，右侧是可读可改的 YAML 编辑器
  （带高亮）。改完点右下角「保存」，提示「已保存并提交到默认分支。」—— **这一步是直接往默认分支
  写一个 commit**，不是开 PR。
- **还没配发布流**：点「新建发布流」，编辑器里装的就是本仓库的发布模板
  （[templates/github/workflows/release-target.yml](../templates/github/workflows/release-target.yml)），
  看一眼、改一改，再点「保存」就把它写成这个仓库的 `.github/workflows/release-target.yml`。

想让模板开箱即用，还要在仓库根放一份发布清单 `.github/release-console.yml`（格式见
[README](../README.md#发布清单仓库里的一份-yaml)）。没有清单也能跑：模板按内建的四个平台
（macos-arm / macos-intel / windows / linux）各构建一次。

另外还有一个「新建工作流」的表单入口：填文件名、名称、操作系统版本、触发方式（手动 / push /
pull_request / 定时）、可选运行容器，再加若干 Job（标识 / 名称 / 运行命令），「预览」看生成的
YAML，「推送」提交到默认分支。适合从零搭一条简单的 CI。表单里还有一颗「使用发布模板」：不用填表，
直接把发布流写进仓库（和上面「新建发布流 → 保存」是同一份文本）。

---

## 4. 先手动跑一次（可选，但推荐）

在工作流列表里点某条 workflow 左边的 ▶：控制台用 `workflow_dispatch` 在默认分支上触发一次，
并把「运行记录」抽屉打开，让你盯着这次运行。

抽屉里是一张表：运行状态 / 工作流名称 / 运行结果 / 分支 / 触发方式 / 执行时间，点表头可排序，
上方输入框「按分支过滤」。每一行最右边：

- 还没跑完 → 「取消」（连同没跑完的 job 一起停）；
- 已完成 → 「删除」（连同它的日志与构建产物一起没）。

刚触发的运行会是「排队中」→「进行中」→「已完成」，控制台在你停在这个页面时会自动刷新。

---

## 5. 读一次运行：job、步骤、日志、产物

在运行表里点「工作流名称」那一列，进入 **运行详情**：

- **Jobs**：每条 job 一行，下面是它的步骤——步骤用编辑器呈现（带行号，可选中、可复制），
  一步一行：编号、名字、结论。行首「查看日志」读这条 job 的原始日志。
- **日志**：上方「在日志中搜索」框按关键词过滤；「复制日志」把当前（过滤后的）文本放进剪贴板；
  「下载运行日志包」把整次运行的日志 zip 下到本地。
- **构建产物**：这次运行产出的 artifact 列表，每条一个「下载」。
- **发布事实**：这次运行自己的输入（版本 / 目标 / 配置）、跑完没有、能下载什么、有没有登记发布。
- 「在浏览器打开」跳到 GitHub 上这次运行；「返回运行列表」回到表格。

---

## 6. 从运行列表直接拿产物

不用进详情也能拿产物：在运行表里， **「已完成」这三个字本身就是按钮**（提示语：「点开看这次运行
产出的构建产物。」）。点它：

1. 控制台去问 GitHub 这次运行产出了什么；
2. **真有可下载的产物**，就在这一行 **下面**展开一块详情（还在表格里），列出每条产物的名字、大小
   （过期的会标「已过期」）和「下载」；没有产物就只在状态栏说一句「这次运行没有可下载的构建产物。」；
3. 点「下载」：那一行的按钮变成 **进度条 + 取消**，状态栏同步出现「文件正在写入 <绝对路径> 中」；
4. 下完：进度条与取消消失，行里变成「文件已经保存到 <绝对路径> 中」后面再跟一颗「下载」
   （想再下一遍就再点）；同时右上角弹一条提示，写着同一个路径；
5. 中途反悔就点「取消」：请求被掐掉，不会留下半个文件。

## 7. 发布看板：用通道 tag 发一次版

标题栏右侧点「← 发布看板」。这里把"发布"从"在控制台里记一笔"变成了 **在仓库里建 tag**。

**看板长什么样**

- 行 = 发布清单里的 **发布目标**（本仓库是 web-arm / web-intel / windows / mas / linux-tar）；
  带模拟步骤的目标名字后面标「模拟」。
- 列 = 三条 **通道 tag**：LTS / latest / dogfood。
- 一格 = 这个目标在这次 tag 的运行里走到哪儿了：`待构建 / 构建中 / 已发布 / 失败 / 已取消`
  （带模拟步骤的目标停在「待签名公证」），下面写着认领到的 job 名字，再下面一颗「查看运行」。
  没有这个 tag 的运行就写「还没有这次 tag 的运行」。

**发一次版**

1. **分支**：下拉里是这个仓库现在的分支（进仓库时读一次），选一条。
2. **提交**：换分支后自动读这条分支上最近的提交，下拉里是 `短 sha · 提交信息`。不挑也行，
   默认用这条分支的最新提交。
3. **版本**：下拉里就是三条通道（lts / latest / dogfood），选你要发的通道。
4. 点「创建」。控制台在仓库里把这个 tag 指到你选的提交上——已经存在就 **移动**它
   （通道 tag 天生是移动的："latest 现在指哪次构建"就是"latest 这个 tag 现在指哪个提交"）。
5. 状态栏提示「已把通道 tag 指到这个提交。」，随后控制台把运行列表刷新一遍。

**推上去之后会发生什么**

这个 tag 是一次 push 事件，触发发布工作流（模板 `on.push.tags: ['**']`，任何 tag 都跑）。
工作流里 `plan` 读清单展开成一张矩阵（每个发布目标一条），各平台分别构建打包，最后把产物挂到 **触发这次构建的那个 tag** 的 Release 上。

看板会按 tag 认领这次运行（tag push 的运行里，`head_branch` 就是 tag 名），取它的 job，按 job 名
`目标名 · 平台/架构 · 产物` 对到每一行。所以你会看到 windows / macOS / Linux 各行的状态从
「构建中」依次变成「已发布」或「失败」——想看细节点那格的「查看运行」，直接落到运行详情
（带日志与产物）。

**版本号是怎么来的**

通道 tag 不是版本号。发布工作流的规矩是：tag 名像版本（`v1.2.3`、`1.2.3`）才当版本用，否则用
`Cargo.toml` 里的版本。所以 `latest` 这次构建出的产物仍然叫
`github-action-console-0.1.0-windows.msi`，挂在 `latest` 这个 Release 上；Windows Installer
另算一个合法的 `x.x.x.x`（`0.1.0.0`）。

## 8. 常见问题

**建了 tag，但没有任何运行**

按顺序查：

1. tag 指向的 **那个提交**里，`.github/workflows/release-target.yml` 的触发条件是否包含它
   （模板现在写的是 `on.push.tags: ['**']`，任何 tag 都行；旧提交可能还写着 `v*`）；
2. tag 是"创建/移动的那一刻"才发 push 事件—— **已经存在的 tag 不会追溯触发**，把 tag 移到新提交
   才会重新发一次；
3. 仓库的 Actions 是否被禁用、workflow 是否在默认分支上能被 GitHub 识别。

**状态栏说权限不足**

「凭据权限不足。需要 repo + workflow（粗粒度 PAT），或 Contents: RW、Actions: RW、
Workflows: RW（细粒度 PAT）。」——按这句话去补 token 权限，然后登出重登。

**限流**

状态栏右侧常显「限流余量：N（重置时间）」。触到限流时提示会告诉你稍后再试，等重置即可。

**MSI / dmg / pkg 打包失败**

那是 CI 那一侧的问题，控制台只旁观：点开那次运行 → 找到失败的 job → 读它的日志。打包链路里
常见的两类坑，本仓库都踩过并记在
[issue 04](../.scratch/multi-platform-release/issues/04-ci-build-chain.md)：Windows Installer 的
代码页（`LGHT0311`）与 64 位组件（`ICE80`）。

**签名、公证、商店提交**

这些步骤没有证书与账号，CI 里一律标注为 **模拟**（`::warning::[SIMULATED] …`），看板上带模拟步骤
的目标最多到「待签名公证」，不会显示"已发布"。这是设计如此，不是失败。

**Linux 上登不进去 / 提示凭据失效**

token 存进 Secret Service（gnome-keyring / KWallet 之类）。容器或精简桌面里可能没有它，
这时要么装上并启动一个 keyring 守护进程，要么每次都重新登录。

**下载大文件时界面卡吗**

不卡：下载在后台任务里跑，界面保持可交互，进度条来回走、随时可取消。但要清楚一点——GitHub 的
产物下载没有流式接口，整个文件会先进内存再落盘，所以 **特别大的产物（几百 MB 以上）会吃掉相应
的内存**。

## 9. 你让 GitHub 发生了什么

用这个控制台时，写操作只有这几类（其余都是读）：

| 动作                                         | 对 GitHub 做了什么                                                        |
|----------------------------------------------|---------------------------------------------------------------------------|
| 保存工作流 / 推送新建的工作流 / 采用发布模板 | 往**默认分支**写一个 commit（改动一个 `.github/workflows/*.yml`）         |
| 左列 ▶                                       | 一次 `workflow_dispatch`                                                  |
| 看板「创建」                                 | 建一个 tag（`POST /git/refs`）；同名 tag 已存在则移动它（`PATCH`，force） |
| 运行记录里的「取消」/「删除」                | `POST /actions/runs/{id}/cancel`、`DELETE /actions/runs/{id}`             |
| 下载产物 / 日志包 / 发布资产                 | 只读                                                                      |
